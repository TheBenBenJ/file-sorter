# file-sorter

*Formerly `tri-icloud` (renamed on 03/11/2026, with its folders, log and environment variables; its scripts, files, options and subcommands got English names the same day).*

Automatic filing of personal documents into a numbered folder tree on iCloud Drive (and Google Drive for office files). A model proposes a destination and a clean name for each new file (a local model for the files whose text can be read, Claude for scans and images); a plain Python script validates the proposal and moves the file. Nothing is ever overwritten, and when in doubt the file stays where it is. The documents already filed are read again too, a few at a time: each one is kept, archived or sent to the trash, so that the theme folders hold only what is still of use.

Why: documents arrive from many places (the phone, the browser's Downloads, invoices received by mail) and end up as `Document (1).pdf` in a pile. Filing them by hand is a chore; letting an AI move files on its own is a risk. Here the AI only reads and proposes, and the script decides.

The code, its file names and its options are in English. The documents' folders and names, the naming convention and the prompt are French, because the tree and the names it produces are French (`00 À trier`, `50 Travail`, `2026-01-15 Fournisseur - Facture 42.pdf`).

## How it works

Inboxes: Google Drive `00 À trier`, the main one (the Mac pours the documents of its `~/Downloads` into it); Google Drive `00 Factures entrantes`, filled every hour by an Apps Script that imports invoices from Gmail (`gmail-invoices.gs`, kept out of this repo); what the phone saves into the Drive without choosing a folder: Chrome's « Enregistrer dans Drive » puts it in a folder of its own, `Enregistré depuis Chrome` (`Saved from Chrome` in English), the Files app at the Drive's root (documents only there: PDF, images, office and iWork files; anything else is left where it is); iCloud `00 À trier`, where the phone's downloads land (on an iPhone, neither Safari nor Shortcuts can choose a Google Drive folder); and, read last, Google Drive `00 Pièces jointes`, where the owner's mail sorter (a separate, private repo) exports every document attached to his mails, received and sent, once per content, named `<date of the mail> <subject> - <original name>` so that the date and the subject help the decision.

For each file at least 60 seconds old (15 per pass): a short text extract (`pdftotext`, `textutil`, the XML inside office files) or an image preview, then the files with text go to a local model (an OpenAI-compatible API, `FILE_SORTER_LOCAL_URL`: on the home server, llama.cpp's `llama-server` with Qwen 3.5 9B; no tool, a strict JSON schema, a few files per question) and the others (scans, images: the local model reads no image) to one `claude -p` call with the Read tool only. The model answers in JSON for each file: destination, new name, confidence, reason. With `FILE_SORTER_SHADOW=1` (the home server's setting from 04/11/2026, until the owner lifts it), Claude still decides for every file and the local model's answers for the files with text are only compared: each file they would not file the same way, folder or name, is a `shadow:` line of the log. The script validates and acts:

- confidence below 0.7, or a destination outside the existing tree (one new sub-folder level is allowed): the file stays in its `00 À trier` (an invoice from Gmail, a download of Chrome's folder or of the Drive's root, or one of `~/Downloads` in the original mode, is moved to the Drive's, so that the root stays tidy; a mail attachment stays in `00 Pièces jointes`) and is remembered in `kept.json` so it is not asked about again;
- never overwrite: a name already taken gets ` (2)`;
- an exact copy (SHA-1) of a document already filed in iCloud goes to the Trash, never deleted;
- editable files (`.docx`, `.xlsx`, `.pptx`…) go to the same path in the Drive, where the Apps Script converts them to Google Docs and Sheets; finished documents (PDF, images) go to iCloud, the archive;
- photos and screenshots keep their name;
- from `~/Downloads`, only documents (PDF, images, office and iWork files, text, CSV) of 50 MB at most go to the Drive; installers, archives, videos and bigger files stay in Downloads (a too big document is reported once), are never deleted, and are listed on the dashboard after 7 days.

### The review of the theme folders: keep, archive or trash

Filing is not enough: temporary documents whose use is over, several copies of the same identity card, terms of sale and other attachments of no interest pile up in the theme folders. So the server's pass (`sort.py --decide`) also reads again the documents already filed, when the inboxes leave the models free: one folder at a time, 10 documents per pass at most, the numbered folders of iCloud and then of the Drive (`10 Identité & Banque/Identité`…). Never the `00` inboxes, the archive, `80 Images` and the settings' `paquets`, a code project, a file at a root or outside the numbered folders, nor a document modified in the last three hours (being written, or just saved). Each document gets one of three decisions, deduced by the same models as the filing (the local model for the files with text, even under `FILE_SORTER_SHADOW`; Claude for scans and images), with the list of every file of its folder as context and today's date:

- **garder** (keep): still current or useful (a valid identity document, a running contract, lease or insurance, a diploma, a civil status record, invoices, payslips and tax notices of the current year and the two before);
- **archiver** (archive): no longer of daily use but worth keeping as a proof (an expired or replaced document, an ended contract, older invoices and payslips): moved into the archive folder at the same path, `90 Archives/10 Identité & Banque/Identité/…`;
- **supprimer** (trash): of no interest (terms of sale or of use, notices, legal notices, advertising, generic documents that are not personal, a temporary file whose use is over), or a lesser copy of another document of the same question (a blurrier scan, a photo of a document already scanned). Never deleted for good: the Drive's trash, or the Mac's Trash for iCloud.

The script decides on the answer: from a confidence of 0.7, a document the model wants out of its folder leaves it, to the trash from 0.9 and into the archive below, where nothing is lost; under 0.7 it stays (the owner's choice of 05/11/2026: with 0.8 to archive and 0.9 to trash, four lesser copies of a replaced identity card stayed while their best one went to the archive). An answer goes to the file it names exactly, or loosely (accents, case) only when no other file of the question could be meant (« Facture (2).pdf » and « Facture 2.pdf » are never confused). A copy leaves only when the one kept in its place (named in `doublon_de`, or by its full name in the reason when the model forgot it) was in the same question (the model saw both) and does not leave as a copy itself, so that one of them always remains; a copy that names no kept one stays, and of two documents whose reasons name each other one stays. Identical files (same size, same SHA-1) are found without a model, the best-named one kept. A folder of 10 documents or fewer is read whole, so that a new copy meets the former ones; a bigger one is read in chunks of 10, in name order. The documents the review already sends to the archive (a proposal of the trial, a decision waiting) are set aside, neither counted nor listed, so that a folder is asked about as it will be: a new identity card meets the copies that stay (06/11/2026). Those going to the trash stay in the question, so that the guard on copies sees both. A document is read again after six months (what was current may no longer be); one left without an answer is asked again an hour later, then a day, then a month, alone from its second miss (one per pass; a model out of reach or at its usage limit counts as no miss, the whole review waits instead), so that a document a model always refuses never holds the walk, nor the documents asked with it, back. A document read again only with its folder keeps its former decision when the model does not answer for it. A proposal already in the journal is not logged again when its folder is read again. The owner's `rules.md` is part of the question too: a rule there ("keep payslips for five years") overrides the defaults. When these rules change (`REVIEW_RULES`, kept in `review.json`), each folder where a document stayed for lack of certainty is read again whole at once, the walk starting over. Nothing of the Google Drive goes to the trash (the owner's rule of 06/11/2026): what the review would trash there goes into the Drive's archive, the journal saying why (« à l'archive plutôt qu'à la corbeille : rien n'est supprimé dans le Drive »); the trial's former proposals to trash there were turned into proposals to archive, once, with one « revu » saying so.

`FILE_SORTER_CLEANUP` says what happens to the decisions:

- `trial` (the default, and any value but `on` and `off`): nothing moves. Each decision to archive or trash is a proposal in the activity journal (« à archiver », « à supprimer »), each folder read a « revu » with its counts, and the end of the first walk over every folder is notified once (counts only). The decisions are kept in `review.json`.
- `on`: the proposals of the trial are carried out first (40 per pass at most), then each new decision at once: inside the Drive by the server itself, into its archive only, into iCloud's archive or the Mac's Trash through the plan (`archiver`, `supprimer`). The Mac checks them again (a source in a theme folder, never an inbox, the archive, `80 Images` nor the settings' `paquets`; an archive target inside the same root's archive; a copy trashed only while the one kept in its place is still there, in its folder or in the archive; the size unchanged), moves or trashes a document only in the cloud without downloading it, and removes the folders an action left empty, down from the third level (a year, a quarter, a former case; never a theme folder nor its first sub-folders).
- `off`: no review. Back to `off` or `trial`, the review's actions the Mac has not carried out yet leave its plan at the next pass (« annulé » in the journal); their decisions wait in `review.json`, and what the Mac had already fetched and does anyway is still logged.

Once every folder is read, the next walk starts an hour later at the earliest; a model out of reach pauses the review for an hour, never the inboxes. The archive folder is an existing `NN Archives` at the root of iCloud or of the Drive (`90 Archives` in the Drive), else `archives` of `settings.json` (default `90 Archives`), created on the first move. The archive is not offered to the filing model as a destination: documents are filed by theme, and the review archives them when their time has passed.

### Two ways to run it

**Split (in service): a home server decides and files the Drive, the Mac files iCloud.**

```
   Server (Linux, timer every 5 min)                                      Mac (relay agent every 5 min)
 Drive 00 À trier ──────┐ read-only mounts
 Drive 00 Factures ─────┤
   entrantes            │
 Drive Enregistré ──────┤
   depuis Chrome, root  ├─► sort.py --decide ──┬─► inside the Drive, itself (rclone):
 iCloud 00 À trier ─────┤ (local model, Claude)│   editable files filed, doubtful invoices
 Drive 00 Pièces ───────┘                      │   and downloads into 00 À trier, duplicates
   jointes (mails)                             │   to its trash; the review's archive and trash
                                               └─► plan.json ───────── pulled ──────► sort.py --apply
                                                                                      ├─ checks every action again
                        ◄────────────── results.json ◄──────── pushed ────────────────┤─ moves into iCloud (from the Drive's
                                                                                      │  inboxes through Google Drive for desktop)
                                                                                      ├─ duplicates to the Trash
                                                                                      └─ documents of ~/Downloads ──► Drive 00 À trier
 vat check ──► sort.py --deposit icloud <path> <file> ──► "deposer" action ──► the Mac writes the report
```

The server reads iCloud and the Drive through read-only mounts. Inside the Drive it files itself, through an rclone remote allowed to write it (`FILE_SORTER_DRIVE_RCLONE`): so the Drive is sorted even when the Mac sleeps. Into or out of iCloud, only the Mac moves: it fetches the plan, applies it and sends back what it did; a finished document waiting in a Drive inbox reaches iCloud that way, the Mac reading it through Google Drive for desktop. The server never connects to the Mac: when the Mac sleeps, those files simply wait in their inbox.

Plan actions (`plan.json`): `ranger` (file it at `cible`), `doublon` (to the Trash), `vers_a_trier` (a doubtful invoice into the Drive's `00 À trier`, when the server cannot move it itself), `deposer` (write a document handed over by the server), and the review's `archiver` (a document of a theme folder into the archive, at `cible`) and `supprimer` (a document of an iCloud theme folder to the Trash, never one of the Drive; for a copy, `garde` is the one kept in its place, which must still exist). An action's id is a hash of type, root, path and size. The Mac answers in `results.json` with `ok`, `absent`, `modifié depuis la décision` or `erreur : …`, and says nothing yet for an iCloud file that is not downloaded.

**Original: everything on the Mac.** `sort.py` alone decides and moves (a launchd agent watching the inboxes, and every 30 minutes). `sort.py --dry-run` shows what it would do. This mode is also the rollback of the split one; the two never run at the same time.

### Other scripts

- `audit.py`: no AI; writes `tidiness-state.json` (loose files next to sub-folders, names outside the convention, files waiting in an inbox for more than 7 days, `00 Pièces jointes` excepted: it keeps doubtful attachments on purpose) for a dashboard. `sort.py` runs it after each pass on the Mac.
- `rename.py plan|apply|undo`: bulk renaming of existing documents according to `convention.md`. `plan` writes `data/rename-plan.json` and a `.tsv` to review, `apply` keeps an undo journal (`data/rename-undo.json`), `undo` restores the names.
- `apply_plan.py verify|apply|undo`: applies a tidying plan (a JSON list of `move` and `trash` operations) after checks, with an undo journal in `data/` (`undo-tidy-<date>.json`).

## Setup

Requirements: Python 3.9+ (standard library only), a local model behind an OpenAI-compatible API with its `/tokenize` (llama.cpp's `llama-server`) for the files with text, the Claude Code CLI (`claude`) for the others, `pdftotext` (poppler). On macOS, `trash`, `brctl`, `sips` and `textutil` come with the system; on Linux, `heif-convert` (libheif) reads iPhone photos.

```sh
cp settings.example.json settings.json   # owner description, Drive path, folders where loose files are fine
cp rules.example.md rules.md             # filing rules, injected into the prompt
cp convention.example.md convention.md   # naming convention, injected into the prompt
mkdir data                               # journals of rename.py and apply_plan.py
python3 sort.py --dry-run
```

`settings.json` keys: `proprietaire` (who the documents belong to, quoted in the prompt), `drive` (Drive path relative to the home folder), `paquets` (folders the audit and the review skip), `vrac_autorise` (folders where loose files are fine) and, optional, `archives` (the review's archive folder when a root has no `NN Archives` yet; `90 Archives` by default).

| Variable | Meaning | Default (the Mac) |
|---|---|---|
| `FILE_SORTER_ICLOUD` | iCloud Drive root | `~/Library/Mobile Documents/com~apple~CloudDocs` |
| `FILE_SORTER_DRIVE` | Google Drive root | `~/` + `drive` of `settings.json` |
| `FILE_SORTER_DATA` | folder of `plan.json`, `results.json`, `applied.json`, `kept.json`, `sort.lock`; on the server also `activity.jsonl`, `run-status.json` (below) and `review.json` (the review's decisions and where its walk stands) | the script's folder |
| `FILE_SORTER_INBOX` | another iCloud inbox, for a trial | iCloud `00 À trier` |
| `FILE_SORTER_DRIVE_INBOX` | another Drive inbox, for a trial | Drive `00 À trier` |
| `FILE_SORTER_ATTACHMENTS_INBOX` | another inbox of mail attachments, for a trial | Drive `00 Pièces jointes` |
| `FILE_SORTER_DRIVE_RCLONE` | server: rclone remote allowed to write the Drive (`gsort:`); unset, only the Mac moves | unset |
| `FILE_SORTER_DOWNLOADS_MAX_MB` | largest download poured into the Drive | `50` |
| `FILE_SORTER_CLAUDE` | `claude` binary, for the files without text (and every file in shadow mode) | `/opt/homebrew/bin/claude` |
| `FILE_SORTER_MODEL` | Claude's model | `haiku` |
| `FILE_SORTER_LOCAL_URL` | the local model (OpenAI API) for the files with text; `off`: none, those files wait (`SANS RÉPONSE`) | `http://127.0.0.1:11234` |
| `FILE_SORTER_SHADOW` | `1`: Claude decides for every file, the local model's answers are only compared (`shadow:` lines); the review is not concerned | unset: the local model decides for the files with text |
| `FILE_SORTER_CLEANUP` | the review of the theme folders (above): `trial` proposes, `on` archives and trashes, `off` stops it | `trial` |
| `FILE_SORTER_MIN_AGE` | seconds a file must stay unchanged before it is handled (a trial; `tests.py` sets 0) | `60` |

`rename.py` and `apply_plan.py` also read `ROOT` (another root, e.g. the Drive), and `rename.py` reads `SUFFIX` (separate plan files), `EXCLUDED` (folders to skip, separated by `|`) and `DOCS_ONLY` (rename documents only).

Scheduling: on the server, a timer runs `python3 -I sort.py --decide` with `FILE_SORTER_ICLOUD`, `FILE_SORTER_DRIVE` and `FILE_SORTER_DATA` pointing at the read-only mounts and a data folder; the personal files are copied next to the code. On the Mac, an agent fetches `plan.json` into this folder, runs `sort.py --apply` and sends `results.json` back. (The units and the relay live in a separate, private repo.)

The file names above are shared between the server, the Mac and a dashboard, and the JSON keys inside the files are French: both are a contract. Rename a file only together with every program that reads it, and keep the keys.

## Operations and troubleshooting

Checks after any change: `python3 -I tests.py` (offline: a sandbox with the example settings, a fake `claude`, a fake local model and a fake `rclone`; it also measures the local model's questions against its slot; the CI runs it too).

Activity journal and step report (`sort.py --decide` only: the server is their single writer; the Mac writes neither), for the System tab of the owner's dashboard, in `FILE_SORTER_DATA`:

- `activity.jsonl`: one JSON event per line, appended: `{"time", "action", "object", "from", "to", "detail", "engine", "model", "confidence", "run"}`, French actions and texts: `rangé` (the destination, the new name included, the model's reason), `renommé` (old name → new name), `doublon` (the original it repeats), `gardé` (left in its inbox, with the reason), `à trier` (a doubtful invoice moved to the Drive's `00 À trier`), `sans réponse`, `échec` (a move in the Drive, or a whole pass: once per series of failed passes, then `rétabli`); for the review, `revu` (a folder read: how many documents, kept, archived, trashed), `à archiver` and `à supprimer` (the trial's proposals, nothing moved), `archivé` and `supprimé` (with the reason, or the copy kept in its place); and, read back from `results.json` at the next pass, what the Mac did: `rangé par le Mac`, `doublon jeté par le Mac`, `déposé par le Mac`, `mis à trier par le Mac`, `archivé par le Mac`, `supprimé par le Mac`, `annulé` (the file was gone or had changed; or an action of the review withdrawn from the plan) or `échec` with its error. The decisions the Mac carries out are logged once `plan.json` is written, so a pass that fails before is not logged twice. File names are allowed there, never in a notification. Mode 600; past 5 MB, rewritten with the last 90 days (20,000 lines at most). A write that fails never stops the pass.
- `run-status.json`: `{"time": start of the pass, "steps": {"inboxes", "decide", "drive", "plan", "icloud": "ok" | "skipped" | "running" | "failed: <message>"}}`, the workflow's steps, rewritten atomically at each change: a pass that fails, or that systemd stops, shows the step it was at. `icloud` speaks of the Mac's results read at this pass; while the Mac has actions to apply and nothing came back, it has no state. Messages are French and never name a file.

Logs: on the Mac `~/Library/Logs/file-sorter.log`; on the server the service journal. Each line starts with a French keyword that docs and habits search for: `RANGÉ` (filed), `GARDÉ` (left in `00 À trier`), `DOUBLON` (duplicate to the Trash), `DÉPOSÉ` (document written), `VERSÉ` (a download poured into the Drive's `00 À trier`), `LAISSÉ` (a download that is not a document, left in Downloads), `PLAN` (server decision), `MAC` (status returned by the Mac), `ERREUR`, `SANS RÉPONSE` (no answer for that file, retried; the local model's reason when it was asked), `shadow:` (`FILE_SORTER_SHADOW=1`: a file the local model would file otherwise, the size of each of its questions in tokens, a summary of each pass), `ATTENTE` (file or folder not available yet, retried), `TROP GROS`, `À DÉPOSER`; for the review, `RELU` (a document and its decision), `REVU` (a folder read, the end of a walk), `ARCHIVÉ`, `SUPPRIMÉ`, `BILAN` (below) and, on the Mac, `VIDÉ` (an empty folder removed). `BILAN` lines hold what `review.json` says, folder by folder, logged once per value of `REVIEW_BILAN` in `sort.py` (a new value, a new bilan at the next pass): the coding agents cannot open `review.json`, and read it there through the unit's journal. Each line is « i/n » then JSON, `[{"r": root, "f": folder, "d": [[name, code, …]]}]`, 16,000 characters at most (a big folder goes on in the next line): `g` kept (its certainty; when the model wanted it out without enough certainty, what it wanted and why), `a` to archive and `s` to trash (certainty, reason), `x` a move that failed, `f` a format the review does not read, `u` without an answer, `n` not read yet; a last line gives the totals. Notifications are French too: macOS notifications on the Mac, a `notifier` command on the server.

| Symptom | Cause | Remedy |
|---|---|---|
| « Resource deadlock avoided » (Errno 11) | the iCloud or Drive file is only in the cloud, and a launchd job may not download it by default | `sort.py` allows itself to (`setiopolicy_np`, at start on the Mac); `materialize()` also asks `brctl download` for iCloud and retries on the next pass |
| A file is never filed | it was left (`GARDÉ`), or the model skipped it or did not answer (`SANS RÉPONSE`: with the local model, its reason, for example `injoignable` or `trop long pour un créneau`) | read the log; remove its line from `kept.json` (server: `name|size`, Mac: `name|size|mtime`) to have it examined again |
| A file waits in `00 À trier` | Mac asleep, plan not fetched yet, mounts a few minutes behind | wait for the next pass, or run the relay by hand; an action not returned within 7 days is dropped by the server |
| A rule or convention change has no effect | the server has its own copy of the personal files | copy `settings.json`, `rules.md` and `convention.md` to the server again |
| A document was archived or trashed by mistake | a decision of the review (`archivé`, `supprimé` in the journal, with the reason) | archived: move it back from `90 Archives`, the path is the same; trashed: the Mac's Trash keeps it 30 days (the review trashes nothing in the Drive). A rule in `rules.md` keeps its kind from then on; `FILE_SORTER_CLEANUP=off` in the server's unit stops the review |
| The review never reaches a folder | the inboxes keep the models busy, a model is out of reach (an hour's pause; the same documents are asked three times at most before the walk goes on), or the walk is resting (an hour after the last folder) | read the journal (`REVU`, `review:`, `SANS RÉPONSE`); `review.json` says where the walk stands. A `review.json` that cannot be read is started again, the inboxes are not held back |

Before deploying a change: `python3 -I -m py_compile sort.py`, then `python3 -I sort.py --dry-run` on the Mac, or `--decide` with `FILE_SORTER_INBOX` and `FILE_SORTER_DATA` pointing at trial folders.

`gmail-invoices.gs` is deployed by hand in Google Apps Script and is kept out of this repo (personal mail queries and folder ids). Automation never modifies it; a change is pasted into the Apps Script editor by a person.

## Security

- No secrets in the repo. Personal files (`settings.json`, `rules.md`, `convention.md`, `kept.json`, `gmail-invoices.gs`) and all state files are ignored by git, under their former French names too; the `*.example.*` files show their format.
- Documents are untrusted input, and a document can try to give instructions. Claude runs with `--tools Read --allowedTools Read` (it can read, not write, move or run anything), `--strict-mcp-config` with no MCP server (no connectors: no mail, no drive, no web), `--setting-sources project` (no user settings, hooks or permissions), `--no-session-persistence`, and `--add-dir` limited to the inboxes and the preview folder. The local model gets no tool at all: it only answers in a strict JSON schema (one answer per file, the names of the files asked as a closed list, strings of bounded length), at temperature 0 and without thinking. Either answer is data that the script checks the same way; the worst a crafted document can do is get itself filed in a wrong existing folder, under a wrong cleaned name, or left in the inbox. A file of the Drive's root that Claude must read itself is handed over as a copy in the preview folder: `--add-dir` never opens the whole Drive. In the review, Claude may read only the folder under review (and the previews); there a crafted document could also get documents of its own folder archived (moved, at the same path, into the archive) or sent to the trash (kept 30 days), each one in the journal with its reason: the trial shows what the review would do before anything moves.
- The server reads through read-only mounts and cannot write into iCloud. In the Drive it writes only through `sort.py`'s own calls: a file of an inbox moved into the tree (the destination validated as for the Mac: an existing folder or one new level, a cleaned name, never an inbox; the name checked against Google first, so nothing is overwritten), a doubtful invoice moved into `00 À trier`, a duplicate sent to the Drive's trash, and, once the review's trial is lifted, a document of a theme folder moved into the archive at the same path (the review never trashes in the Drive); nothing is deleted for good. Google has no narrower grant than the whole Drive for files the server did not create, so the grant is kept in the server account that runs the sorting and nowhere else.
- The Mac checks every action again: paths must stay inside iCloud or the Drive, the source must be in an inbox (in a numbered theme folder for the review's actions, never the archive, the photos nor the bundles), the target never an inbox (inside the same root's archive for `archiver`; `supprimer` never in the Drive; for a copy to trash, the one kept in its place must still exist), and the size must not have changed since the decision.
- Server notifications go to a public push service, so they never contain file names.
- Text extracts (up to 2,500 characters, 1,200 for the review) go to the local model, which keeps them on the machine that runs it, and to Claude too in shadow mode; unreadable files go to Claude: judge whether that suits your documents.

## Design decisions

- **The model proposes, the script decides.** Rather than letting an agent move files with write tools, the model only reads and answers in a fixed JSON schema; the script accepts only existing folders (plus one new level), a confidence of at least 0.7, cleaned names and never an overwrite. Doubt means the file stays.
- **The server decides, the Mac moves** (adopted on 03/11/2026, the owner's idea), **and the server files the Drive itself** (the owner's decision the same afternoon). The main inbox is in the Drive, where the Mac pours its downloads (the phone's land in iCloud's inbox, the only kind of folder iOS lets Safari and Shortcuts choose): editable documents stay in the Drive and are filed there by the server, even with the Mac asleep; finished documents go to iCloud, the archive, through the Mac. Rejected: the server writing into iCloud with rclone, whose iCloud backend is still experimental and whose repeated failures could lock the Apple account. Cost: a grant on the whole Drive on the server (see Security), and finished documents still wait for the Mac.
- **Downloads: documents only, 50 MB at most.** Everything poured into the Drive is uploaded, and a finished document comes back down when the Mac files it in iCloud: installers, archives and videos have no place in the archive, and a big file would cost two transfers for nothing. They stay in Downloads, never deleted by the sorting, and the dashboard lists them after a week.
- **Idempotent plan.** Action ids come from the content (type, path, size); the Mac remembers applied ids for 7 days (`applied.json`), so a plan fetched twice is applied once; the server drops actions never returned within a week and remembers handled sources for an hour, because the mounts show changes a few minutes late.
- **`kept.json` signatures differ by machine**: `name|size|mtime` on the Mac, `name|size` on the server, because a file the Mac moves keeps its name and size but not its date.
- **Mail attachments: a fourth inbox, read last, that keeps its doubtful files** (03/11/2026, the owner's wish that every attachment of his mail goes through the sorting, the backlog once, then new mail). The mail sorter exports each document once into the Drive's `00 Pièces jointes`, at about the pace of the sorting (40 files every 15 minutes, 15 decided every 5). A doubtful attachment stays there, remembered in `kept.json`, instead of joining `00 À trier`: a mailbox's backlog (some 1,600 files here) would bury the documents the owner drops himself; for the same reason the folder is read after the other inboxes and the audit does not list its files as waiting. Duplicates of the archive go to the Drive's trash, like any other inbox's. An attachment the model proposes no new name for stays too: its export name never follows the convention, and the model does that when it recognizes a copy of another document of the batch (the same photo sent again, re-encoded), which its answer cannot send to the trash; only identical bytes go there. Files already planned for the Mac no longer count among a pass's 15: they held back the next ones while the Mac slept or the mounts lagged.
- **Downloads go through the Drive's `00 À trier`.** The server cannot see the Mac's Downloads; pouring them into the single inbox keeps one place where decisions are made.
- **Duplicates by size, then SHA-1**: only files of the same size are hashed, which keeps the walk of iCloud cheap.
- **One lock per data folder**: a pass that finds another running exits; `--deposit` waits for the lock, so a report is never lost.
- **The local model for the files with text, Claude for the others** (04/11/2026, the owner's decision): the routines that only classify lines of text left Claude for the home server's model, free and independent of the subscription's usage window (on 03/11/2026 sessions had used it up for three hours); file sorting follows for the files whose text `extract()` reads. Scans, images and HEIC previews stay with Claude and its Read tool: the local model reads no image, and OCR was declined. The local model starts in shadow mode (`FILE_SORTER_SHADOW=1` in the server's unit): Claude decides, and each disagreement on the folder or the name is logged, so that the owner judges it on real files first. Lifting the shadow means removing that line from the unit; the files with text then never reach Claude, even when the local model does not answer: they wait, `SANS RÉPONSE`.
- **15 files per pass**: Claude (Haiku) reads the files without text in one call; the local model gets up to 5 files with text per question, measured with its own tokenizer against its slot of 16,384 tokens, the tree, `rules.md` and `convention.md` taking their share (5 files with a usual tree, 3 with a very big one, in the tests); a question it still refuses as too long is asked again in halves. A pass loops until the inboxes are empty.
- **A review of what is filed: keep, archive or trash** (05/11/2026, the owner's request: only what is still current in the theme folders, the best of several copies, no attachments of no use; the existing documents first, then the same rules for what comes next). A review of the folders rather than a fourth answer at filing time: one place decides, with the folder's other files in view (a newer card, a better scan), for the documents filed years ago as for those filed yesterday, and again six months later, when a current document may have expired. One folder per pass, when the inboxes leave the models free, so that the inboxes never wait and Claude's usage stays small; the files with text go to the local model even under the shadow (the review is new, there is no former behaviour to compare with), which keeps Claude for scans and images. Archive at the same path, so that a document goes back with one move; trash, never a deletion. A trial first (`FILE_SORTER_CLEANUP=trial`, the default): every decision shows in the journal before anything moves, and lifting the trial applies those very decisions, not new ones. Rejected: deciding at filing time only (the documents already filed, the reason of the request, would stay); a model that moves files itself; deleting for good.
- **Nothing of the Drive to the trash** (06/11/2026, the owner's rule before lifting the review's trial: « sur la partie google drive faut faire en sorte de rien supprimer »). The Drive holds the editable documents of his work and studies, which the trial proposed to trash by the dozen (course materials, templates, old CVs). What the review would trash there goes into the Drive's archive instead, where nothing is lost and the path is kept; the server never sends the Mac a `supprimer` for the Drive, and the Mac refuses one. iCloud keeps the trash for what is of no use. The duplicates of the inboxes (identical bytes) still go to the Drive's trash: the original stays filed.
- **What the phone saves into the Drive is an inbox too** (05/11/2026, the owner's request in ticket 14: « Faudrait que ça trie aussi ces fichiers-là »). Chrome on the iPhone saves into its own `Enregistré depuis Chrome` folder, which it creates again at each save, and the Files app at the root: both are read like the Drive's `00 À trier`, after it. The folder itself is left in place, empty: removing it while Chrome saves into it could send the download into the trash with it.
- **French where it is a contract**: the prompt and its answer keys (the names must stay French), the keys and values inside the plan and result files exchanged between two machines updated separately, the log keywords and the notifications. The code was translated to English on 03/11/2026 without changing any of them.
- **English names for files, options and subcommands** (03/11/2026, the owner's wish: everything technical in English). A file name has a few known readers (the Mac relay, the server's units, the dashboard, two skills), so the names changed in one switch together with those readers and the files on both machines. The JSON keys stayed French: they live inside the files the two machines exchange, so changing them would need both sides to read both forms for a while. An unknown option now stops `sort.py` (it used to fall back to the full mode, which decides and moves), and an unknown command stops `apply_plan.py` (it used to only check): a caller left with a former name fails loudly.
